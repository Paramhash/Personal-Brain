# [[adr-035-promotion-workflow|ADR-035]] — Promotion Into `/production/src/` Is a Dispatched Development Action, Identified by Content Digest

- **Date:** 2026-09-26
- **Status:** Active. **Untested** — no promotion has ever been performed; see Consequences.
- **Context:** The dual-root design has required from the beginning that code enter `/production/src/` "only through a completed, validated promotion from the development environment", and `/development/claude.md` §4 reserves `docs/meta/` for "workflows and process definitions". That directory was **empty**, so the promotion the design mandates was never defined: no document said who may write `/production/src/`, what constitutes a validated artifact, how it is identified, or how it is reversed. Read literally, the two standing prompts appeared to leave nobody able to perform one — `production/claude.md` §1.3 says the directory is entered "never by your edit", and `development/claude.md` §2 forbids the Implementer from promoting "on your own initiative". The gap became blocking rather than theoretical when the observation recorder became the first artifact that needs promoting: DRAFT TICKET F's controlled-promotion step said "promote the validated artifact" with no mechanism behind it, so the ticket would have halted there. A second, smaller problem compounded it: the draft asked for a "source revision", and **this repository is not a git repository** — `git rev-parse` fails from the workspace root — so the artifact had no identity to record either.
- **Decision:** Author `docs/meta/promotion_workflow.md` as the binding process. Its load-bearing decision is that the apparent deadlock is not one, and the difference in the two prompts' wording is the resolution: production mode is forbidden **absolutely** ("never by your edit"), while development mode is forbidden only **unilaterally** ("on your own initiative"). **A promotion is therefore a development-mode action performed by the Implementer, and only under an explicit dispatched promotion ticket.** The human operator authorises it by staging that ticket; the SRE never promotes, and hands defects back to development instead. Around that: artifact identity is a **content digest** over the promoted set plus the Node and npm versions, since there is no revision to name; the promoted set is exactly `dist/**`, `package.json` and `package-lock.json`, and never an environment file, key material, `src/`, `docs/`, `todo/` or `node_modules/`; dependencies are reproduced on the host with `npm ci --omit=dev` rather than vendored; the previous `/production/src/` is copied to `/production/.rollback/<utc>-<digest>/` **before anything is written**, even when empty; a promotion never starts the promoted process, because activation is a separate supervised step with its own preflight; and **every promotion record must state whether the artifact holds capital, a signer, and venue write access.**
- **Consequences:** The recorder's promotion has a defined mechanism, so DRAFT TICKET F splits cleanly into a development-mode promotion ticket and an operator/SRE activation ticket, and neither crosses a root boundary. Rollback becomes a nameable action rather than an aspiration, and it needed no new authority: `production/claude.md` §2 already lists "roll back to the previous validated version" among the SRE's permitted mitigations, and restoring a previously validated artifact authors nothing, so the absolute prohibition on editing is untouched. The mandatory capital statement matters most for the very first promotion, because `production/claude.md` opens with "real capital, real positions" and leads its incident procedure with preserving capital — correct for the trading binary and wrong for a read-only recorder, and an SRE who cannot tell which they are looking at will spend an incident applying capital-preservation mitigations to something that has none. The costs are real. **This workflow is untested**: no promotion has been performed against it, and the first execution should be treated as an exercise of the process as much as of the artifact, with amendment expected. `/production/.rollback/` is a new path that `production/claude.md` §5's directory map does not list, and that map should be amended to include it with read-only access for production mode — a standing-prompt change, flagged here rather than made. Content digests are also weaker than revision control: they identify an artifact but carry no history, no authorship and no diff, so a promotion can be verified but not explained. That is adequate for now and should not be mistaken for sufficient.
- **Alternatives rejected:** **Promote TypeScript sources and build on the production host** — it makes production a workspace, which `production/claude.md` §1.3 explicitly denies ("a receptacle, not a workspace"), requires a compiler toolchain there, and puts a build step inside the environment least able to absorb a build failure. **Vendor `node_modules` into the promoted set** — the tree carries platform-specific native binaries and `@solana/web3.js` and Anchor both pull them; development runs `darwin/arm64` and the NUC need not, so a vendored tree is not portable, whereas the exact-pinned lockfile already *is* the validated closure and `npm ci` reproduces rather than resolves it. **Let the SRE perform promotions**, since they are already on the production host — rejected because §1.3 forbids it absolutely, and more importantly an SRE who can promote can patch: the prohibition and the dual-root split exist to make "fix it here" impossible, and a promotion power in production mode would quietly restore it. **Let the Implementer promote whenever the validation gate passes** — it would make the human's authorisation implicit and contradicts §2's "on your own initiative"; validation establishes that an artifact *could* be promoted, not that it *should* be. **Initialise git to obtain revision identity** — genuinely the better long-term answer, and rejected here for scope and for safety: `.env`, `.env.bak-20260919-dupip` and `devnet-keypair.json` sit in the development root and are currently protected only by the absence of version control, so introducing git without first establishing ignore rules and secret hygiene creates a credential-commit risk larger than the identity problem it solves. Content digests solve identity today; revision control remains worth doing deliberately, as its own ticket. **Combine promotion and activation into one step** — it crosses the root boundary in a single ticket and skips the smoke-test gate that stands between a copied artifact and a 21-day run. **Handle promotion ad hoc in each ticket that needs one** — this is precisely how the gap arose, and it guarantees the process is re-derived differently every time, with the rollback point being the part most likely to be skipped under time pressure.

## Amendment note — 2026-10-01 16:43Z: the workspace is now a git repository

- **What changed:** [[adr-035-promotion-workflow|ADR-035]] chose content digests because "this repository is not a git repository". That is no longer
  true. The workspace has been a git repository since 2026-09-26 (first commit `1417294`), pushed to `origin`.
- **The secret-hygiene concern behind rejecting git has been met:**
  - `.gitignore` excludes `.env`, `.env.*` and `*.env`;
  - `devnet-keypair.json` and the `.env.bak-*` file it named no longer exist in the development root;
  - no key or env file is tracked.
- **Effect:** the content digest stays the artifact identity, because it is what the destination check verifies.
  A promotion record should **also** name the commit the artifact was built from. That gives the history, authorship
  and diff the original Consequences section said digests lack.
- **Still true:** [[adr-035-promotion-workflow|ADR-035]] remains untested; no promotion has been performed.
