# [[adr-015-fsm-cold-start-and-ev-gate|ADR-015]] — Macro FSM Cold-Start Deployment Path and the EV Gate

- **Date:** 2026-09-17
- **Status:** Active
- **Context:** The bot cannot deploy from a cold boot. `transitionMacroState`'s `MONITORING` case only ever transitions to `THREAT_EVALUATION` or `DEFENSIVE_WITHDRAWAL` — the only way to reach `REGIME_OBSERVATION` and then `REDEPLOYMENT` is through `DEFENSIVE_WITHDRAWAL`'s confirmed-exit edge, which presupposes a position existed to withdraw. A fresh boot with no active DLMM position therefore rests in `MONITORING` forever, `REDEPLOYMENT` is never entered, no `ExecutionIntentEvent { action: 'REDEPLOY' }` is ever emitted, and Step 6 of the deployment runbook (`dry_run_transaction`, the evidence execution builds and simulates without broadcasting) has accordingly never been observed on any pre-flight run. Separately, `readVenueState` in `src/index.ts` returns `ev: null` because `src/decision/ev/` does not exist, so the EV gate the cold-start path itself would need to pass is permanently absent rather than merely unpassed.
- **Decision 1 (Cold-Start):** Add a reconciled `hasActivePosition_t: boolean` fact to `MacroFsmInputs`, sourced the same way `withdrawal` and `redeployCompleted_t` already are — a fact the operational layer reconciles and the macro reducer consumes, never recomputes (F-004 invariant 2). In `MONITORING`, when the regime is safe (`regimeLabel_t === 'POSITIVE_GEX'`), the EV gate passes (`ev !== null && ev.gate_pass`), and `hasActivePosition_t` is `false`, transition directly to `REDEPLOYMENT` (not through `REGIME_OBSERVATION`), emitting `ExecutionIntentEvent { action: 'REDEPLOY', priorityFeeMode: 'NORMAL' }` on entry exactly as the existing `REGIME_OBSERVATION → REDEPLOYMENT` edge already does. `REGIME_OBSERVATION`'s stabilization guards (`stableTimeOk`, `stableSnapshotsOk`) exist to enforce a cool-down after a defensive exit; a cold start has not just been through a threat event, so re-using that state would either invent new semantics for entering it unprovoked or force an arbitrary wait with no threat to wait out. Going directly to `REDEPLOYMENT` reuses the existing entry-intent logic unchanged and adds exactly one new edge.
- **Decision 2 (EV Gate):** Author `src/decision/ev/evCalculator.ts` to construct the `EvDecisionPayload` `ev_policy.md` §3 fixes, computing `net_ev = projected_dynamic_fees - projected_lvr_quote - binance_funding_drag` exactly, and setting `gate_pass` by calling the existing `meetsEvHurdle()` in `src/config/strategy.config.ts` rather than re-evaluating the `1.5 * (swap_slippage + gas_fees)` inequality a second time — `ev_policy.md` §6 forbids a second EV rule and the config surface already owns `evHurdleMultiplier` and `meetsEvHurdle`. Wire it into `Orchestrator.readVenueState()` so `ev` is a populated payload instead of `null`. `projected_dynamic_fees`, `projected_lvr_quote`, `binance_funding_drag`, `swap_slippage`, and `gas_fees` have no ratified estimator yet (F-001/Q001 propose the LVR model but no blueprint fixes a production fee, funding, slippage, or gas forecaster); each is therefore taken as an injected function with a clearly labeled placeholder implementation, following `config_contract.md` §5's existing permission for boundary-layer injection of unratified values — the same pattern already used for `HedgeRiskConfig`. A placeholder producing a real, non-fabricated number that unblocks the gate is acceptable; a placeholder that always returns a value engineered to pass is not, and would make `gate_pass` decorative.
- **Consequences:** The EV gate becomes reachable rather than permanently `null`, and a bot with a positive regime, a passing EV gate, and no position can now deploy from a cold boot without requiring a prior withdrawal to manufacture the transition. Step 6 becomes reachable through the normal path for the first time. The cost is that every EV component feeding `net_ev` is a provisional estimator rather than a ratified model; `docs/status/current.md` must carry this the same way it already carries the four other unratified runtime inputs, so the gate's passing is not mistaken for a calibrated economic judgment.
- **Alternatives rejected:** Route the cold-start path through `REGIME_OBSERVATION` — reuses a state built for post-withdrawal stabilization and either invents new entry semantics or imposes an arbitrary wait unrelated to any threat; fabricate a non-null `EvDecisionPayload` with `gate_pass` hardcoded `true` until real estimators exist — makes the gate decorative and defeats the purpose of gating at all; re-implement the hurdle inequality inside `evCalculator.ts` — duplicates `meetsEvHurdle` and creates two places the multiplier can drift apart, which `ev_policy.md` §6 forbids outright.
