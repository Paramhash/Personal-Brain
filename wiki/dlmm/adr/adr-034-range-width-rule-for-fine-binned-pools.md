# [[adr-034-range-width-rule-for-fine-binned-pools|ADR-034]] — The Deployed Range Width Is Derived From Volatility, and the GEX Walls Only Bound It

- **Date:** 2026-09-26
- **Status:** Active. Introduces one **UNRATIFIED** constant, `deployWidthSigmaMultiple`, and ratifies no other.
- **Context:** `range_planning.md` §2 fixed the deploy bounds *equal* to the Put and Call walls, and neither that blueprint nor `rangePlanner.ts` carried any maximum width, clamp or rejection. [[adr-023-range-planner-devnet-scaling-and-containment|ADR-023]] added active-bin containment and explicitly rejected letting the adapter "repair or clamp an out-of-range plan", so a plan of any width is produced and accepted by design. That was invisible while the only pool in use had 80 bps bins, where the walls observed in soak15 (`putWallStrike_t: 103`, `callWallStrike_t: 150` near spot 120, 37.6% wide) enclosed 47 bins — a single bin array, a single chunked transaction, a deployable position. The verified mainnet SOL/USDC target `5rCf1DM8LjKTw4YqhnoLcngyZYeNnQqztScTogYHAS6` has **4 bps** bins, twenty times finer, where the same 37.6% encloses roughly **940 bins**. Three consequences follow, and none of them is an execution defect: fees accrue only in the active bin, so **939 of 940 bins earn nothing at any instant — 99.89% of deployed capital** — against a `PLACEHOLDER_DLMM_CONCENTRATION_MULTIPLIER = 1.8` that encodes a concentration *benefit* such a position does not have; 940 bins spans roughly **14 bin arrays** where [[adr-030-deployment-sol-reserve|ADR-030]]'s `0.25 SOL` reserve was sized for at most **two** uninitialized ones, and 13 uninitialized arrays would cost `0.0434 + 13 × 0.0714 = 0.9721 SOL` against a 1.266 SOL wallet, so [[adr-030-deployment-sol-reserve|ADR-030]]'s own guard would refuse the deployment with `INSUFFICIENT_SOL_RESERVE`; and wall spacing is an options-structure quantity while bin width is a pool-geometry quantity, with nothing making them commensurate. `chunkBinRange` is not implicated — it splits 940 bins into 14 legal chunks correctly.
- **Decision:** The GEX walls become an **envelope** the deployed range may not leave, and the width *inside* that envelope is derived. `range_planning.md` §2b fixes the rule: `targetHalfWidthPct = deployWidthSigmaMultiple × sigma × sqrt(horizonSeconds)`, converted to bins at the pool's own `binStep`, then `width = clamp(2 × targetHalfBins + 1, MIN_BINS_PER_POSITION, envelopeBins)`, placed as a window containing the active bin, centred on it and shifted inward only as far as the envelope requires, with an odd remainder going to the lower side first. Applied in a fixed five-step order with two named rejections before any width is computed: an inverted envelope or one narrower than `MIN_BINS_PER_POSITION`, and an active bin outside the envelope. `sigma` and `horizonSeconds` are the inputs `ev_policy.md` already consumes, and the width is recomputed per plan rather than frozen. `deployWidthSigmaMultiple` defaults to **1** and is labelled **UNRATIFIED** in the same terms as the EV placeholders; `observation_archive.md` §6 question 3 — the fraction of wall-clock time the active bin stayed inside a range of width *W* — is named as its ratifier, and it needs only the `active_bin_id` scalar series.
- **Consequences:** On the mainnet target the derived width is **203 bins** where wall-to-wall was 940: bin arrays drop from 14 to 3 and chunked transactions from 14 to 3, and the walls never bind, since they sit 347 and 538 bins from the active bin against a σ half-width of 101. On the 80 bps Devnet pool the σ-derived width is 13 bins, below the floor, so the **20-bin minimum binds** and soak15's 47-bin plan would become 20 — narrower and more concentrated. Both geometries remain deployable and neither is wall-to-wall, which is the property the rule exists to guarantee. **The width rule is necessary and not sufficient:** 3 uninitialized arrays still cost `0.2577 SOL`, above [[adr-030-deployment-sol-reserve|ADR-030]]'s ratified `0.25 SOL`, so even the tightest defensible width breaches the reserve and [[adr-030-deployment-sol-reserve|ADR-030]] must become width-aware. That is routed to its own ADR rather than settled here, because this ticket's guardrails forbid reopening the reserve. A volatility-derived width also inherits σ's uncertainty — and σ is quadratically consequential in the EV gate, where a 1.5× error moves the pass threshold from 7.38 to 12.14 bps/day — but it inherits it in a **self-correcting direction**: higher volatility widens the range, which is what a wider excursion requires, whereas a fixed cap is wrong in an unknown direction. A further consequence is that the planner's negative-bin path is now load-bearing on a pool whose active bin is `-5311`, and no committed test outside the observation suite exercises a negative `activeBinId` through containment, chunking and deployment.
- **Alternatives rejected:** **A maximum bin count per position** — 69 bins is 2.76% of price at 4 bps and 55% at 80 bps, so a bin rule means something different on every pool, and it imports a per-transaction limit into a question about where price goes; `MAX_BINS_PER_POSITION` is the chunker's constraint and using it as policy would conflate planning with execution. **A fixed maximum percentage width** — pool-independent, but a bare constant with no derivation behind it, which is the failure this repository keeps paying for, and it would not move when σ is measured. **Fail-closed rejection whenever wall spacing exceeds an approved width** — retained as a guard for the envelope-too-narrow case, but rejected as the primary rule: on the fine-binned pool the walls almost always exceed any sane width, so this would mean never deploying on the pool the strategy is built for, which is abandonment rather than policy. **Letting the deployment adapter clamp or repair an oversized plan** — [[adr-023-range-planner-devnet-scaling-and-containment|ADR-023]] already rejected this and the reasoning stands: it silently changes approved intelligence, and the width belongs to the planner that owns the bounds. **Keeping wall-to-wall and raising the reserve to fund 14 arrays** — it would cost roughly 0.97 SOL of rent to hold a position that leaves 99.89% of its capital idle, which pays for the dilution instead of fixing it. **Deferring until σ is measured** — the width rule's *structure* does not depend on σ's value, only its multiple does, and leaving the planner with no width fence at all while a mainnet run is prepared is the larger risk.
